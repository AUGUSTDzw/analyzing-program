# 代码忠实度检查：修好之后测到什么

## 一、先修的是我自己的探针

第一版把**代码块**拿去源码里找**连续**匹配，结果在 AVE 报告上报出 92.5 处"不可验证"。逐条查证
后：**全部是误报** —— 都是 `SAPGUI_PROGRESS_INDICATOR` 的调用，而源码里有 **30 处**该 FM 调用，
报告引的是其中另一处（`*10`/`lv_filter_total`），只是换行方式不同。三段特征文本在源码里
全部 FOUND。

**连续性是错的判据**：报告可以分片引用一个构造，换行和缩进都允许不同。判据应该是
**"有没有哪一条引文在源码里根本不存在"**。

这是本项目第七次同型错误：探针的名字和它实际度量的东西不符。

## 二、现在的判据

逐行判定，一条引文只要在源码里出现即算忠实。不要求块连续。跳过三类**不对源码作声明**的行：

| 跳过 | 理由 |
|---|---|
| 含 `...` / `…` 的行 | skill 明确允许样板清单省略 |
| 纯括号注释行 | 报告自己的说明 |
| 含中文且无 `\|` 的行 | 报告自己的批注混入代码块 |
| 引号数为奇数的行 | 报告排版残留 |

归一化处理：大小写、连续空白、标点前空格（源码写 `t_documents ,`，报告写 `t_documents,`）、
括号后空格。

## 三、负向对照

前两版控制组本身是错的（一版查错了报告的行，一版改的文件正好是检查会跳过的风险层片段），
都报了"失败"而那不是检查的问题。

现在通过：

**能在真实改动上触发、还原后清零。**

## 五、16 条候选里我验证了 3 条

| 候选 | 源码实际 | 性质 |
|---|---|---|
| `ftpost 'K' '1' 'BKPF-BLDAT' ls_bseg-bldat.` | L481 是 `is_bkpf-bldat` | **实质失真** |
| `TYPES tt_blart TYPE HASHED TABLE OF blart` | L73 无 `TYPES` 前缀（`TYPES:` 另起一行） | 合并语句 + 丢冒号 |
| `lv_provider = wire_of( lv_id );` | L17611 逐字相同，但句末是 `.` 不是 `;` | 标点替换 |

第一处值得单独说：报告引用的那段 `SELECT ... bukrs,belnr,gjahr,buzei,koart,umskz FROM bseg`
**根本没选 `bldat` 字段**，所以 `ls_bseg-bldat` 即使在报告自己的逻辑下也不存在。源码用的是
另一个结构 `is_bkpf-bldat`。这正是 skill 明令禁止的"改源码语句让引用更好读"。

**其余 13 条我没有验证。**

## 六、准确的表述

不能说"失真率 1.1%"。能说的是：

> **候选率 1.1%（16/1444）。已验证：1 条实质失真、2 条标点级偏差、13 条未验证。**

把它接成闸门硬判定是错的：16 条里至少 2 条是标点噪声，若判失败就是在制造假警报，
而假警报会让整个闸门失去可信度 —— 这正是本项目反复踩的坑。

所以它留在 `analyzing-programs-workspace/` 作评估工具，**不进 skill 的闸门**，
直到那 13 条被逐条定性。

## 七、这回答了"是否足够保证正确性"

补上了闸门缺的一环：skill 要求"贴出的代码必须逐字符忠实于源码"，此前无人检查，
而这项**机械可判**。

仍然查不了的：内容是否正确（v1 有 6 条错误论断）、召回率（无参考答案无法测）、
以及生成可靠性（FI toolkit 5 次失败、AVE 截断）。
