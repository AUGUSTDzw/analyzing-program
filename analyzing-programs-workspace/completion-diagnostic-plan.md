# completion-diagnostic：大文件为什么静默失败

**状态：待执行。预测表在生成之前写死，先提交本文件再派发。**

## 1. 要回答的问题

iteration-9b 的唯一正结果：在 1115–1598 行的真实 ABAP 源码上，
一次无提示派发产出可用报告的概率约 **42%**（5/12），失败形式是
**静默**——没有残篇、没有报错，就是没有文件。

样本太小（每个尺寸 4 次），看不出失败是尺寸驱动的，还是随机的。
在能测出版本差异之前，必须先知道 42% 这个数到底是什么造成的。

三种互斥的机制，各自有可检验的预测：

| | 假设 | 预测 |
|---|---|---|
| M1 | **输出量受限**——报告太长，一次吐不完 | 同一份大源码上，把输出压到几十行就成功；恢复长输出又失败 |
| M2 | **输入/上下文受限**——源码太大，装不下 | 不管输出多短，大源码上都失败；小源码上都成功 |
| M3 | **纯随机**——模型偶发静默 | 输出长短、源码大小都不改变完成率 |

M1 是可以修的（skill 里改成增量写文件）。M2 是硬约束（得改输入方式）。
M3 是运气（只能靠重试堆样本）。三者的后续动作完全不同，所以必须分开。

## 2. 条件

全部单模型、单轮、无提示词额外干预，除 D3 外。
每个条件 3 次派发，每次独立。

| 条件 | 源码 | 任务 | 输出量 | 次数 |
|---|---|---|---|---|
| **D1** | 1598 行（objects_program） | skill 全流程报告 | 长 | 3 |
| **D2** | 1598 行（同上） | 只列方法名+起止行+一句话职责 | 短 | 3 |
| **D3** | 1598 行（同上） | skill 全流程报告，**要求增量追加写** | 长 | 3 |
| **D4** | 332 行（最大合成夹具） | skill 全流程报告 | 长 | 3 |

- **D1 vs D2 是关键对照**：同一份源码、同一个代理类型，只有输出量不同。
  它把 M1 和 M2 分开。
- **D2 不加载 skill**，直接给任务。目的是把"输出量"这个变量单独拎出来，
  不被 skill 的指令长度污染。
- **D3 是机制探针，不是修复验证**：它测的是"增量写"能不能改善完成率。
  它的 prompt 与 D1 不同（多了增量追加的要求），所以 **D3 的数据不能
  混进任何版本对比**——它只回答"M1 是否成立、且是否可修"。
- **D4 是尺寸基线**：小源码上完成率应接近 100%。若 D4 也低，
  说明 M2 不是"大"引起的，M3 的嫌疑变大。

D2 的短任务明确定义（避免"短"变成模糊概念）：

> 读源码，为每个方法/子程序写一行：名称、起始行号、结束行号、一句话说明
> 做什么。不要写任何其他内容。目标是几十行的清单，不是分析报告。

## 3. 判定（读表，事先写死）

设 `L` = D2 完成率（大源码+短输出），`H` = D1 完成率（大源码+长输出），
`S` = D4 完成率（小源码+长输出）。

| L | H | S | 结论 |
|---|---|---|---|
| 高 | 低 | 高 | **M1**：输出量受限。且 D3 若高于 D1 → 增量写可修 |
| 高 | 高 | 高 | **M3**：完成率本身没问题，42% 是别处的噪声 |
| 低 | 低 | 高 | **M2**：输入/上下文受限。大源码上短输出也救不了 |
| 低 | 低 | 低 | **M2 或 M3**：无尺寸信号，靠重试堆样本 |
| 高 | 低 | 低 | 混合，样本不足，加次数重测 |

"高"= ≥2/3，"低"= ≤1/3。样本只有 3 次，所以**这个判定只有方向性意义，
不能当功效结论**。它的用途是决定下一步做什么，不是给完成率下断言。

## 4. 明确不做的

- **不用这批数据算版本差异。** D3 的 prompt 不同，D2 不加载 skill。
  这批数据只回答机制，不回答版本。
- **不用它更新 iteration-9b 的结果。** 单独归档在 `completion-diagnostic/`。
- **不在派发前看结果改预测。** 预测表已在本文件里。

## 5. 记录

每个条件的每次派发：尝试号、是否产出文件、文件行数、失败是否静默。
工具级中断（`Tool execution aborted`）**不算一次尝试**，重派。
静默无输出**算一次尝试**——那正是要测的东西。
