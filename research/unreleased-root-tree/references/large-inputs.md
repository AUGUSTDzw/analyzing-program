# 大输入：一次任务写不完

**这是观察，不是规则。** 下面每一条都有测量，但**没有测过任何解法**。
所以这个目录只记录发生了什么，不告诉你该怎么做 —— 把观察当建议用，
就是又一次基于弱证据的改动。

SKILL.md 的正文里没有这些数字：它们描述的是「一次任务可能产不出完整报告」，
不是「报告该怎么写」。只有当输入很大、或者输出看起来像被截断时才需要看。

## 三条实测事实

1. **文件大小不预测失败。** 1464、1784 行失败，而 1988、2079、3257 行成功。
   不要按行数决定要不要担心。→ `budget-exhaustion.md`
2. **失败都死在第三节**（`## 三、分组分析`），句子断在半途，从没走到第四节。
   同一个文件同一套指令，前置章节吃掉 130 行还是 482 行，
   直接决定第三节还剩多少预算 —— 这个方差比写入方式的影响大得多。
   → `budget-exhaustion.md`
3. **完整率 29%，与交付方式无关。** 单次写入、两段写入、切片-即写三种方式分辨不出
   （slice 1/2 对其余 3/12，Fisher p ≈ 0.57），都落在 20–50%。
   → `delivery-methods.md`

## 每个文件讲什么

| 文件 | 内容 |
|---|---|
| `budget-exhaustion.md` | 为什么写不完：大小不预测、都死在第三节、预算方差、瓶颈是预算不是写法 |
| `delivery-methods.md` | 三种交付结构各自的完整率；分段为什么没用 |
| `slice-and-write.md` | 唯一一份通过闸门的 AVE 报告怎么来的（**n=1**） |
| `output-rate.md` | 行/子程序速率随子程序数崩塌；格式没有深度档位 |
| `truncated-reports.md` | 截断的报告比缺失的报告更危险；残篇识别信号 |

## 这个目录里**没有**的东西

没有深度档位规则（例如「子程序超过 N 个时按功能簇分组，每个簇一个代码块」）。
那需要先测 N 是多少 —— **未测，因此没有写进 skill。**
