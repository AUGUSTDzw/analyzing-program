# 产出速率：格式没有深度档位

**这是观察，不是规则。** 每条都有测量，但**没有测过任何解法**，
所以这里不给建议 —— 给了就是又一次基于弱证据的改动。

## 行/子程序

12 份**完成**报告（两重信号筛过：六节齐全 **且** 行数不低于源码的 1/20）
测出的行/子程序：

| 子程序数 | 行/子程序 |
|---|---|
| 439 | **7.4** |
| 62 | 14.1 |
| 20 | 80.0 |
| 18 | 83.6 – 115.5 |
| 9 | 92.6 |
| 7 | 87.0 |
| 2 | 202.5 |

**速率随子程序数上升而崩塌**，中位数 91。三个推论：

1. **18 个子程序、约 1700 行源码，是实测反复成功的规模**（84–116 行/子程序）。
2. **单次约 2000 行的产出，覆盖约 20 个子程序**（2000 ÷ 91）。这是量级估计不是预算 ——
   观察到的两次死亡在 925 行和 1974 行，且都在第三节内部。
3. **439 个子程序的类池，按中位深度需要约 40,000 行**；实测只写出了 3,257 行，
   密度 0.15 —— 被诊断为清单。

所以大输入写不完**不是任务预算问题，是格式的成本没有上限**：
skill 要求「每个源码块跟三层」，但从不说**一个子程序该配几个块**。
18 个子程序时每个能深写 110 行；439 个时每个只能分到 7 行，于是退化成名录。

`report_qc.py` 的密度诊断项就是量这个档位的位置。它在超大文件上**必然触发** ——
因为任何诚实的产出都低于 0.5 块/子程序。这是对的：它在如实报告产出是什么样。

**缺的是档位，不是检测。** 要加深度规则（比如「子程序超过 N 个时按功能簇分组，
每个簇一个代码块」）需要先测 N 是多少 —— 未测，因此**没有写进 skill**。

## 超大文件的实测形态

AVE（29,564 行，439 个子程序）分四段写，仍在第三节耗尽：

```
low density: 41 quoted block(s) for 439 declared subprogram(s) = 0.09 each
             (171 of them named in the text)
```

一份**形状完好**的报告 —— 六节里的前三节齐、代码块三层齐全、Mermaid 可渲染 ——
只覆盖了 171 个子程序中的 41 块代码。这正是 `report_qc.py` 的密度诊断项存在的理由。
