# 大输入：一次任务写不完

**这是观察，不是规则。** 下面每条都有测量，但**没有测过任何解法**，
所以这里不给建议 —— 给了就是又一次基于弱证据的改动。

## 现象

23 份报告里，成功的那些和失败的那些**大小没有区别**：

| 单次写入 | 行数 | 结果 |
|---|---|---|
| v3 r1 / r2（无闸门） | 1988 / 2079 | 成功 |
| AVE v1 | 3257 | 成功 |
| v4（有闸门） | 137 / 392 / 465 / ~1659 / 1464 / 1784 | 全部失败或截断 |

「超过某个行数就失败」不成立 —— 1464、1784 失败，而 1988、2079、3257 成功。
所以不要按文件大小决定要不要担心。

## 真正的规律：失败都死在第三节

`## 三、分组分析` 是逐子程序展开的地方，占报告体量的大头。
**每一次失败的运行都死在第三节内部**，句子断在半途，从没走到第四节。

| 运行 | 行数 | 停在 |
|---|---|---|
| st1 | 1505 | 完成六节 |
| st2 | 925 | 第三节中，句子断在 `ekstre_fblxn` |
| st_ave | 1974 | 第三节中 |

**闸门被排除。** 三次失败都没走到 `scripts/report_qc.py` 那一步，
所以第 6 步的闸门不是原因。

## 预算被前置部分吃掉多少，方差极大

同一个文件、同样的指令：

| 运行 | 第一个 `####` 出现在第几行 |
|---|---|
| st1（成功） | 130 |
| st2（失败） | 482 |

前置章节吃掉 130 行还是 482 行，直接决定了还剩多少预算给第三节。
**这个方差比写入方式的影响大得多。**

## 完整生成成功率：25%

FI toolkit（约 1700 行、18 个方法）的**全部** 12 次尝试，包括什么都没写的那几次：

| 结果 | 次数 |
|---|---|
| 完整（六节齐全） | **3** |
| 截断（2/6 或 3/6 节） | 3 |
| **什么都没写**（空返回 / 中止） | **6** |

**完整率 25%。** 分段写入、单次写入、v3/v4、有无闸门 —— 都在这个 25% 之内，
看不出哪种方式更好。

之前引用过「分段 1/3 对单次 0/4」，那个记录**漏掉了什么都没写的 6 次**。
不记全就会把 25% 读成 33%，把 0/4 读成"从未成功"。

`analyzing-programs-workspace/generation_log.py` 保留这份完整台账。
它的用处和 `truncation_audit.py` 一样：**截断的报告比缺失的报告更危险**，
而"什么都没写"如果不被记录，就会被当成"没试过"。

## 分段写入没有解决问题

试过把一→三 / 四→六 切成两段写：

| 写入方式 | 成功 |
|---|---|
| 单次 | 0 / 4 |
| 分两段 | 1 / 3 |

Fisher 精确检验 **p = 0.333**，与单次写入**分辨不出**。所以分段**没有**写进 skill。

失败原因也清楚：第一段（一二三）本身就超预算，切错了地方。
按第三节的子程序组继续细分是显而易见的解法，**但没测过**。

## 产出速率：格式没有深度档位

12 份**完成**报告（两重信号筛过：六节齐全 **且** 行数不低于源码的 1/20）
测出的行/子程序：

| 子程序数 | 行/子程序 |
|---|---|
| 439 | **7.4** |
| 62 | 14.1 |
| 20 | 80.0 |
| 18 | 83.6 – 115.5 |
| 9 | 92.6 |
| 7 | 87.0 |
| 2 | 202.5 |

**速率随子程序数上升而崩塌**，中位数 91。三个推论：

1. **18 个子程序、约 1700 行源码，是实测反复成功的规模**（84–116 行/子程序）。
2. **单次约 2000 行的产出，覆盖约 20 个子程序**（2000 ÷ 91）。这是量级估计不是预算 ——
   观察到的两次死亡在 925 行和 1974 行，且都在第三节内部。
3. **439 个子程序的类池，按中位深度需要约 40,000 行**；实测只写出了 3,257 行，
   密度 0.15 —— 被诊断为清单。

所以大输入写不完**不是任务预算问题，是格式的成本没有上限**：
skill 要求"每个源码块跟三层"，但从不说**一个子程序该配几个块**。
18 个子程序时每个能深写 110 行；439 个时每个只能分到 7 行，于是退化成名录。

`report_qc.py` 的密度诊断项就是量这个档位的位置。它在超大文件上**必然触发** ——
因为任何诚实的产出都低于 0.5 块/子程序。这是对的：它在如实报告产出是什么样。

**缺的是档位，不是检测。** 要加深度规则（比如"子程序超过 N 个时按功能簇分组，
每个簇一个代码块"）需要先测 N 是多少 —— 未测，因此**没有写进 skill**。

## 超大文件的实测形态

AVE（29,564 行，439 个子程序）分四段写，仍在第三节耗尽：

```
low density: 41 quoted block(s) for 439 declared subprogram(s) = 0.09 each
             (171 of them named in the text)
```

一份**形状完好**的报告 —— 六节里的前三节齐、代码块三层齐全、Mermaid 可渲染 ——
只覆盖了 171 个子程序中的 41 块代码。这正是 `report_qc.py` 的密度诊断项存在的理由。

## 实务上意味着什么

分析大文件时，**预期一次任务产不出一份完整报告**。
如果输出停在第三节中间，那是预算耗尽，不是 skill 失效、也不是闸门没过 ——
**根本没有完整报告可以过闸门**。

截断的报告比缺失的报告更危险：它还是文件、会被计数、看起来像数据。
本项目就因此把一份 465 行的 AVE 残篇当成完整报告计入聚合，
误报出「A8 缺陷从 50 降到 15」。

`analyzing-programs-workspace/truncation_audit.py` 就是为这类事故写的：
按「节数是否齐六」和「每千行源码引用多少代码块」两个独立信号识别残篇。
